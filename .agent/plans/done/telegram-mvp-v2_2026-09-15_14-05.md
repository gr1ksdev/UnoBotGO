# Plano: telegram-mvp-v2 — Milestone 3

## Pedido do usuário

Planejar e, após aprovação explícita, implementar um UnoBotGO V2 executável no
Telegram, permitindo jogar uma rodada completa através de Inline Mode. M1 e M2
estão concluídas e aprovadas. Nesta etapa, o usuário autorizou apenas salvar o
plano; a implementação continua pendente de aprovação.

## Objetivo

Entregar o fluxo:

```text
/novo → /entrar → /iniciar → @usernamebot → selecionar carta
→ confirmação oficial → próximo jogador → GameFinished
```

A mão privada via Inline Mode é a interface principal. Telegram será somente
adapter/apresentação, consumindo internal/game.Service sem engines ou snapshots.

- Na telego v1.10.0, CacheTime usa omitempty: atribuir zero não envia cache_time:0.
- O V1 contorna isso com HTTP paralelo; a V2 usará RequestConstructor da biblioteca.
- A documentação não garante transferência de file_id entre bots. Os IDs atuais
  serão preservados conforme pedido; seu funcionamento será verificado no bot de aceite.

## Estratégia de implementação

### API e composição

- Adapter recebe *game.Service, cliente telego e *slog.Logger por composição.
- Run(ctx) controla execução.
- Interfaces privadas, pequenas e definidas pelo consumidor permitem simular
  serviço/transporte nos testes.
- Não recriar manager de partidas, autorização administrativa ou regras de cartas.
- Cache de nomes limitado a 10 mil usuários, somente apresentação, sem mãos ou
  permissões. Fallback para identificação numérica; escapar HTML.

### Comandos

| Comando | Comportamento |
|---|---|
| /novo | Lobby vazio, autor responsável, BotRules. |
| /entrar | Inscrição explícita via Service. |
| /iniciar | Solicitação do responsável; M2 escolhe dealer padrão. |
| /cancelar | Cancelamento autorizado pela M2; /kill como alias. |
| /sair | Saída normal, incluindo transferência de responsabilidade. |
| /estado | Consulta pública da partida ativa. |
| /ajuda | Instruções e explicação da confirmação oficial. |

Preservar /start como alias de início em grupos; no privado, mostrar ajuda.
Reconhecer /comando@usernamebot e ignorar comandos destinados a outro bot.

Comandos de jogo exigem grupo/supergrupo e autor identificável. Mensagens sem From,
de outros bots ou enviadas como SenderChat não autorizam ações. MVP atende grupos
comuns; tópicos de fórum, canais e operações business recebem orientação de
contexto não suportado, sem criação parcial.

### Transporte e concorrência

Manter telego v1.10.0 e long polling:

- GetMe no startup, verificando username e Inline Mode habilitado.
- Verificar webhook existente e falhar com instrução clara, sem removê-lo automaticamente.
- Registrar apenas comandos implementados.
- Receber message, inline_query, chosen_inline_result e callback_query.
- Usar net/http com contexto e timeout; desabilitar logging bruto da biblioteca.

Preservar ordem das confirmações:

- Oito filas fixas de execução, 32 posições cada, distribuídas por ChatID.
- Comandos e seleções da mesma partida seguem a mesma fila, incluindo aplicação e apresentação.
- Quatro workers separados para consultas inline, com fila limitada a 64 consultas.
- Filas são apenas agendamento; não possuem estado de jogo.
- Saturação recusa trabalho sem executar ação e produz diagnóstico seguro.
- Não criar goroutines ilimitadas.
- Nenhum lock do Service ou token store fica retido durante I/O.

### Configuração e shutdown

Ambiente; .env opcional sem sobrescrever variáveis exportadas:

| Variável | Padrão |
|---|---|
| TOKEN | Obrigatória |
| LOG_LEVEL | info |
| HISTORY_LIMIT | 100 |
| INLINE_TOKEN_TTL | 2m |
| INLINE_TOKEN_LIMIT | 20000 |
| INLINE_TOKEN_USER_LIMIT | 512 |

Validar limites, duração e formato do token sem imprimir valores secretos.

Usar signal.NotifyContext. Interromper polling/admissão, aguardar trabalho admitido
por até dez segundos, cancelar operações restantes e fechar conexões ociosas.
Publicação já aceita pelo Service não será revertida.

Logs estruturados: operação, IDs, revision e classe/código do erro. Nunca TOKEN,
URLs autenticadas, payloads de updates, consultas completas, tokens inline ou mãos.

Falhas de envio não reaplicam ações. Uma repetição apenas para rejeição explícita
429, respeitando retry_after de até cinco segundos e contexto. Timeout de envio
não terá retry automático.

### Localização inline

Consulta contextualizada: g_<GameID>. GameID é referência pública, nunca autorização.

| Situação | Resposta |
|---|---|
| Zero partidas | Resultado informativo orientando /novo e /entrar. |
| Uma partida, consulta vazia | Abrir diretamente a própria mão. |
| Várias partidas, consulta vazia | Lista com nome do grupo e identificador curto. |
| Contexto válido | PlayerView do usuário e jogo indicados. |
| Contexto inválido/encerrado/sem participação | Informação, sem selecionar outro jogo implicitamente. |

Selecionar grupo publica mensagem neutra de navegação com botão “Abrir minha mão”,
preenchendo a consulta contextualizada. Não executa ação nem estabelece current game.

Toda confirmação oficial terá “Suas cartas” com contexto da partida. Não exigir
conversa privada com o bot para jogar.

### Cartas, Wild, Draw e Pass

- Preservar ordem da mão entregue pela M2.
- Carta jogável: sticker normal e token de PlayCard.
- Carta não jogável: sticker cinza na lista privada; seleção publica somente
  orientação genérica, sem revelar carta e sem executar ação.
- Cabeçalho identifica grupo, turno e fase, sem publicar a mão.
- Cópias iguais têm tokens distintos vinculados a CardIDs físicos.

| Estado | Controles |
|---|---|
| Lobby | Aguardar início. |
| Turno alheio | Mão consultável, sem controles de ação. |
| TakingTurn, autor do turno, sem DrawnCardID | Comprar. |
| TakingTurn, autor do turno, com DrawnCardID | Passar e cartas marcadas jogáveis pela M2. |
| ChoosingColor, autor da escolha | Quatro resultados de cor. |

Usar Playable e estado projetado; não calcular combinação, restrição de +4 ou efeitos.

Wild/+4: selecionar sticker → engine entra em escolha → confirmação pede nova
consulta → jogador escolhe cor com token da revision atual → engine resolve
penalidade, turno/colocação. Cobrir Wild inicial e último Wild da mão.

Compra publica apenas quantidade. Se a engine mantiver turno, a nova mão permite
jogar a carta comprada ou passar; se avançar, anunciar próximo jogador.

### Paginação

- Até 45 cartas por página, reservando espaço para cabeçalho e até quatro controles.
- Paginar também seleção de grupos.
- Offset opaco associado a usuário, consulta, posição e contexto.
- Cursor de mão inclui GameID/revision; cursor de grupos identifica a lista consultada.
- Mudança de revision/lista exige reabrir consulta, sem combinar estados diferentes.
- Cursor não armazena snapshot ou mão.

### Seleção e confirmação oficial

Sticker acionável tem teclado “⏳ Aguardando validação” e “Suas cartas”.

Após ChosenInlineResult:

1. Resolver e consumir token autorizado.
2. Service.Apply com autor verdadeiro e revision original.
3. Enviar confirmação/rejeição ao chat cadastrado na partida.
4. Quando disponível, usar inline_message_id para marcar teclado confirmado/recusado.

Confirmação reúne ação aceita, topo/cor, turno/escolha pendente, contagens,
colocações e término. Não enviar outro sticker duplicado da seleção.

Stale: “Seleção antiga: a partida mudou. Abra Suas cartas novamente.” Não repetir
identidade da carta recusada, não alterar estado nem atualizar revision para retry.

Token desconhecido ou de outro usuário não produz mensagem no grupo vinculado ao
token. Quando possível, o resultado selecionado recebe status genérico de recusa.

Callbacks do indicador apenas consultam status e respondem ao usuário; não jogam.
Confirmações terão “Atualizar estado”, consultando GameID explícito, inclusive
resumo final enquanto retido.

### Token store

Store privado em memória, independente da posse de partidas:

```text
token imprevisível de 128 bits, base64url
→ tipo: ação ou cursor
→ userID
→ gameID/chatID quando aplicável
→ action/cardID/color/revision para ação
→ criação/expiração
→ estado de consumo e resultado público resumido
```

- Emissão em lote antes da resposta inline.
- Verificar usuário antes de consumo.
- Consumo atômico antes de Apply; só um concorrente obtém a ação.
- Sucesso ou erro do Service encerra token; não recolocar em circulação.
- Reuso não executa ação nem duplica confirmação oficial.
- Reter marcador de resultado até expiração; apagar detalhes privados após processamento.
- Encerramento/saída/colocação invalidam descritores pendentes do jogo/participante.
- Leitura não renova expiração; limpeza oportunista, sem timers ou serviço de limpeza.
- Evicção FIFO, limites global e por usuário; consumidos também contam.
- Expiração/evicção/restart exigem nova consulta.
- Relógio e aleatoriedade injetáveis nos testes.
- Cursor é leitura, com tipo separado; nunca pode ser consumido como ação.

### cache_time e privacidade

RequestConstructor trata especificamente AnswerInlineQueryParams, emitindo
cache_time:0, is_personal:true e next_offset explícito, inclusive vazio. Demais
parâmetros/métodos seguem construtor padrão; não criar HTTP paralelo nem atualizar telego.

Actor vem de From.ID do update. Tokens não comprovam onde o sticker foi publicado;
a ação pertence ao GameID associado na emissão. O estado oficial permanece no
chat cadastrado. Pela escolha confirmada, carta selecionada pode aparecer antes
de ser rejeitada; nenhum outro conteúdo da mão será publicado.

## Riscos

- Feedback deve estar habilitado em 100%; amostragem perde jogadas.
- Sticker pode ser publicado antes da recusa; decisão aceita explicitamente.
- Não há prova do chat de destino em ChosenInlineResult.
- Cache do cliente/resultados antigos continuam exigindo revision e tokens.
- IDs de stickers precisam ser validados no bot de aceite, sem substituição silenciosa.
- Erro de envio após Apply não desfaz ação; consulta pública recupera estado observável.
- Filas limitadas podem recusar trabalho em sobrecarga; não prometer entrega durável.
- Restart perde partidas e tokens; não implementar recovery nesta milestone.

## Como testar

### Build

```bash
go build ./...
docker build -f Dockerfile.v2 -t unobotgo:v2 .
```

### Testes

- Comandos/aliases/destinatário @bot, contextos inválidos e owner observador.
- Integração com Service real: criação, inscrição, início, autorização e cancelamento.
- Fixtures determinísticas de views/erros para cenários específicos do adapter,
  sem expor factories/snapshots da M2.
- Zero/uma/várias partidas, navegação, consultas concorrentes e multigrupo.
- Mão somente do autor, carta normal/cinza, identidade física e escape de nomes.
- Token inexistente, errado, expirado, consumido, concorrente, invalidado e erro de geração.
- Stale sem mutação; tokens distintos da mesma revision aceitam somente uma ação.
- Wild/+4, cor inicial/final, compra/passagem, colocação e GameFinished.
- Mais de 50 resultados, controles em todas as páginas e cursor incompatível.
- HTTP simulado: JSON explícito, erros HTTP/API/429 e logs sem segredos.
- Feedback com/sem inline_message_id; falha de confirmação sem reaplicar ação.
- Ordem por chat, saturação, polling cancelado e drenagem no shutdown.
- Regressões integrais M1/M2/V1 e cobertura dos novos packages.

```bash
gofmt -w cmd/bot internal/config internal/telegram
go build ./...
go test ./...
go test -race ./...
go vet ./...
git diff --check
```

### Execução

Configurar TOKEN em .env local e executar:

```bash
go run ./cmd/bot
```

Alternativa Docker:

```bash
docker run --rm --env-file .env unobotgo:v2
```
